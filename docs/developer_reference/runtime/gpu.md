# gpuArray

numbl implements MATLAB's `gpuArray`: an array held in a GPU device's memory, on which functions and operators run on the device and return gpuArrays. The code is in `runtime/gpu/` and `interpreter/builtins/gpu.ts`.

## Values

A gpuArray is a `RuntimeGpuArray` (kind `gpu_array`): its device, an opaque device buffer, its shape, its underlying class (`cls`: double, single or logical, what `underlyingType` returns), whether it is complex, and the device generation it was made in. `class` gives `gpuArray`; `isa(G, 'float')` and the other categories follow the underlying class, while `isa(G, 'single')` is false, as in MATLAB. The contents are immutable: every operation, indexed assignment included, makes a new array, so a gpuArray never needs copy-on-write. `gather` copies the data back to a host value (a 1x1 double or logical array as a scalar).

## Devices

A device (`GpuDevice` in `runtime/gpu/deviceTypes.ts`) stores data (`upload`, `download`) and says whether it computes in double precision (`supportsDouble`, `gpuDevice().SupportsDouble`). The host lists its devices (`NumblHost.gpuDevices`, a `GpuDeviceSet`), one of which is selected; `gpuDevice(index)` selects and resets one, `gpuDevice([])` deselects, and `reset(D)` resets. Resetting increments the device's `generation`, so the arrays made before no longer exist (`existsOnGPU` is false and using one raises `The data no longer exists on the device.`).

Every host has two CPU reference devices (`runtime/gpu/cpuDevice.ts`), whose memory is host memory: the first computes in double precision and the second does not. They make gpuArray code run and testable without a GPU, and are the reference a real device's results are compared against.

When WebGPU has an adapter, the WebGPU device (`runtime/gpu/webgpuDevice.ts`) comes first, as MATLAB's default device is the GPU. Its data lives in WebGPU buffers owned by the GPU helper, the thread that also serves `gpu.call` for `.numbl.js` files (`src/gpuHelper.ts`): a browser worker started at boot, or in Node a `worker_threads` worker running Dawn from the optional `webgpu` npm package (`src/nodeGpuHelper.ts`), started on first gpuArray use and disabled by `NUMBL_NO_WEBGPU`. The device list is built lazily (`GpuDeviceSet` takes a function), so a run that never uses gpuArray never starts the helper. The helper's gpuArray module (`webgpuModule.ts`) keeps buffers by ids the client chooses, so an upload is posted without waiting; the helper runs posted calls and requests in order, and an error from a posted call is raised by the next request. A download waits for the helper. Buffers are freed when their gpuArray is garbage collected (a `FinalizationRegistry`). WebGPU computes in single precision only (`SupportsDouble` is false): single and logical arrays are stored as f32, and a double array, which can only be an operation's result (the index output of `max`), is kept in host memory.

A device without double precision follows MATLAB's advice to use single on such hardware strictly: creating a double gpuArray is an error that names the fix (`gpuArray(single(X))`). The creations checked are `gpuArray(X)`, the constructors with `'gpuArray'` (`zeros(n, 'gpuArray')` is double), `double(G)` and `cast(G, 'double')`. Results of operations are not checked: single combined with double gives single, and the index output of `max` is double.

## Running builtins on a gpuArray

Every builtin runs on gpuArray arguments, through the call wrapper (`makeBuiltin` in `builtin.ts`) and the argument-kind policy (`runtime/argKinds.ts`): unless a builtin declares `accepts: { gpu: true }`, its gpuArray arguments are gathered to the host before `apply` runs, and its numeric and logical outputs are uploaded to the device of the first gpuArray argument. Text, cells and other outputs stay on the host. A builtin whose results MATLAB leaves on the host declares `hostOutputs: true` (the type predicates, `isequal`); the shape and class queries (`size`, `numel`, `class`, `isa`, `isempty`, `isnumeric`, ...) declare `accepts: { gpu: true }` and read the gpuArray's shape and class without gathering. Builtins that store or pass on a value (`struct`, `setfield`, `deal`, `feval`, `subsref`, `subsasgn`, `builtin`) also take gpuArrays as they are.

Operators reach the same path: a gpuArray is an object (`isObject` in its `KINDS` entry) with registered methods, so `G + 1` dispatches to `plus`, which, having no gpuArray method, is the builtin. Indexing and indexed assignment (`indexIntoRTValue`, `storeIntoRTValueIndex`), concatenation (`Runtime.horzcat` / `vertcat` dispatch to the builtins), colon and `for` loops (`runtimeOperators.ts`), and conditions (`toBool`) gather, compute on the host and upload. Assigning a gpuArray into a host numeric array makes the result a gpuArray. The constructors take `'gpuArray'` (`withGpuOption` in `array-construction.ts`); their `'like', G` form needs nothing special, since the gathered prototype gives the class and the result goes back to the device.

On the CPU reference devices this path is the whole implementation.

## Kernels

A device may run operations natively: `GpuDevice.kernels` (`GpuKernels` in `device.ts`) offers element-wise operations, reductions over one dimension, matrix products and transposes over real f32 data. gpuArray methods registered in `builtins/gpu.ts` try them first (`runtime/gpu/kernels.ts`) and otherwise call the builtin, so the generic path is the fallback. A kernel runs when every operand is a real single or logical gpuArray in the device's memory or a host scalar, the arrays have one shape or one element, and the result is not double (MATLAB's class rules: comparisons and logical operators give logical, arithmetic with a single operand gives single; `L + 1` for a logical `L` is double and falls back). The operations: `+ - .* ./ .\`, unary minus, the comparisons, `& | ~`, two-argument `max`/`min`, `abs`, `exp`, `sin`, `cos`, `tan`, `sinh`, `cosh`, `tanh`, `floor`, `ceil`, `fix`, `round`, `sign`; `sum`, `prod`, `mean`, one-output `max`/`min` (over the first non-singleton dimension, a given one, or `'all'`); `mtimes` and the transposes. Functions whose real inputs can give complex results (`sqrt`, `log`, `power`) are left to the fallback, as are complex arrays, index outputs and broadcasting beyond scalar expansion.

The WebGPU device implements the kernels in WGSL (`webgpuModule.ts`), compiled once per operation and operand kinds; scalars travel in a uniform block. A kernel is posted without waiting, so a chain of operations stays on the GPU until a `gather` (or a condition, a scalar read) waits for it. Each kernel runs in an error scope, so a failure is raised by the next request. NaN is detected on the bits (a shader compiler may assume `x == x`), so `max`/`min` skip NaN as MATLAB does, and `round` rounds half away from zero. Reductions accumulate in f32, splitting a long reduction with few outputs into chunks of 64. The results differ from the host's in the last bits: WGSL allows 2.5 ulp for division and an absolute error of 2^-11 for `sin` and `cos` on [-pi, pi] (and more outside it), and summation order differs; `numbl_test_scripts/gpu/gpuarray_kernels.m` states the tolerances.

In Node, Dawn aborts the process if its device is alive when the helper worker is torn down, so the Node helper shuts the device down (a `shutdown` request) when the process exits. A device with kernels will register gpuArray methods (`classMethod("gpuArray", ...)`) for the operations it runs natively; resolution picks a method of an object argument before the builtin, so the generic path remains the fallback for everything else.

The JIT declines gpuArray values (`typeOfValue` types them as unknown), so code that handles them runs on the interpreter.
