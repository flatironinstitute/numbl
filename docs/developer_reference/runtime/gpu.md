# gpuArray

numbl implements MATLAB's `gpuArray`: an array held in a GPU device's memory, on which functions and operators run on the device and return gpuArrays. The code is in `runtime/gpu/` and `interpreter/builtins/gpu.ts`.

## Values

A gpuArray is a `RuntimeGpuArray` (kind `gpu_array`): its device, an opaque device buffer, its shape, its underlying class (`cls`: double, single or logical, what `underlyingType` returns), whether it is complex, and the device generation it was made in. `class` gives `gpuArray`; `isa(G, 'float')` and the other categories follow the underlying class, while `isa(G, 'single')` is false, as in MATLAB. The contents are immutable: every operation, indexed assignment included, makes a new array, so a gpuArray never needs copy-on-write. `gather` copies the data back to a host value (a 1x1 double or logical array as a scalar).

## Devices

A device (`GpuDevice` in `runtime/gpu/deviceTypes.ts`) stores data (`upload`, `download`) and says whether it computes in double precision (`supportsDouble`, `gpuDevice().SupportsDouble`). The host lists its devices (`NumblHost.gpuDevices`, a `GpuDeviceSet`), one of which is selected; `gpuDevice(index)` selects and resets one, `gpuDevice([])` deselects, and `reset(D)` resets. Resetting increments the device's `generation`, so the arrays made before no longer exist (`existsOnGPU` is false and using one raises `The data no longer exists on the device.`).

Every host has two CPU reference devices (`runtime/gpu/cpuDevice.ts`), whose memory is host memory: the first computes in double precision and the second does not. They make gpuArray code run and testable without a GPU, and are the reference a real device's results are compared against.

When WebGPU has an adapter, the WebGPU device (`runtime/gpu/webgpuDevice.ts`) comes first, as MATLAB's default device is the GPU. Its data lives in WebGPU buffers owned by the GPU helper, the thread that also serves `gpu.call` for `.numbl.js` files (`src/gpuHelper.ts`): a browser worker started at boot, or in Node a `worker_threads` worker running Dawn from the optional `webgpu` npm package (`src/nodeGpuHelper.ts`), started on first gpuArray use and disabled by `NUMBL_NO_WEBGPU`. The device list is built lazily (`GpuDeviceSet` takes a function), so a run that never uses gpuArray never starts the helper. The helper's gpuArray module (`webgpuModule.ts`) keeps buffers by ids the client chooses, so an upload is posted without waiting; the helper runs posted calls and requests in order, and an error from a posted call is raised by the next request. A download waits for the helper.

Device memory is released deterministically: a device may count the gpuArrays that use each buffer (`retain` on construction, `release` from `RuntimeGpuArray._destroy` when the array's reference count reaches zero; see [refcount.md](refcount.md)), since `reshape`, `G(:)` and vector transposes share a buffer. A buffer nothing uses is freed in queue order, after the posted work that reads it; kernel intermediates (the sum inside `mean`, the squares inside `norm`) are released the same way. A wrapper that is never counted (made outside a statement) is freed when it is garbage collected (a `FinalizationRegistry`). Garbage collection alone is not enough: the wrappers are small, so the collector does not run while device memory fills. The helper keeps freed buffers for reuse by size (up to 512 MB), which saves the allocation and the zero-fill of a new buffer and roughly triples element-wise throughput on large arrays; every kernel writes all of its output. `gpuDevice().AvailableMemory` is `TotalMemory` minus the bytes the device's arrays hold. WebGPU computes in single precision only (`SupportsDouble` is false): single and logical arrays are stored as f32, and a double array, which can only be an operation's result (the index output of `max`), is kept in host memory.

A device without double precision follows MATLAB's advice to use single on such hardware strictly: creating a double gpuArray is an error that names the fix (`gpuArray(single(X))`). The creations checked are `gpuArray(X)`, the constructors with `'gpuArray'` (`zeros(n, 'gpuArray')` is double), `double(G)` and `cast(G, 'double')`. Results of operations are not checked: single combined with double gives single, and the index output of `max` is double.

## Running builtins on a gpuArray

Every builtin runs on gpuArray arguments, through the call wrapper (`makeBuiltin` in `builtin.ts`) and the argument-kind policy (`runtime/argKinds.ts`): unless a builtin declares `accepts: { gpu: true }`, its gpuArray arguments are gathered to the host before `apply` runs, and its numeric and logical outputs are uploaded to the device of the first gpuArray argument. Text, cells and other outputs stay on the host. A builtin whose results MATLAB leaves on the host declares `hostOutputs: true` (the type predicates, `isequal`); the shape and class queries (`size`, `numel`, `class`, `isa`, `isempty`, `isnumeric`, ...) declare `accepts: { gpu: true }` and read the gpuArray's shape and class without gathering. Builtins that store or pass on a value (`struct`, `setfield`, `deal`, `feval`, `subsref`, `subsasgn`, `builtin`) also take gpuArrays as they are.

Operators reach the same path: a gpuArray is an object (`isObject` in its `KINDS` entry) with registered methods, so `G + 1` dispatches to `plus`, which, having no gpuArray method, is the builtin. Indexing and indexed assignment (`indexIntoRTValue`, `storeIntoRTValueIndex`), concatenation (`Runtime.horzcat` / `vertcat` dispatch to the builtins), colon and `for` loops (`runtimeOperators.ts`), and conditions (`toBool`) gather, compute on the host and upload. Assigning a gpuArray into a host numeric array makes the result a gpuArray. The constructors take `'gpuArray'` (`withGpuOption` in `array-construction.ts`); their `'like', G` form needs nothing special, since the gathered prototype gives the class and the result goes back to the device.

On the CPU reference devices this path is the whole implementation.

## Kernels

A device may run operations natively: `GpuDevice.kernels` (`GpuKernels` in `device.ts`) offers element-wise operations (with implicit expansion up to four dimensions), reductions over one dimension, matrix products, transposes, and gathers and scatters of selected elements, over real f32 data. gpuArray methods registered in `builtins/gpu.ts` try them first (`runtime/gpu/kernels.ts`) and otherwise call the builtin, so the generic path is the fallback; indexing (`indexIntoRTValue`) and indexed assignment (`storeIntoRTValueIndex`) try `indexKernel` and `storeKernel` the same way, with the selection planned on the host (`planIndex`, `planStore`), so the index rules and error messages are the host's. A kernel runs when every operand is a real single or logical gpuArray in the device's memory or a host scalar, the arrays have compatible shapes, and the result is not double (MATLAB's class rules: comparisons and logical operators give logical, arithmetic with a single operand gives single; `L + 1` for a logical `L` is double and falls back). An assignment that grows the array, deletes elements or stores non-logical values into a logical array falls back. The operations: `+ - .* ./ .\ .^`, unary minus, the comparisons, `& | ~`, two-argument `max`/`min`, `abs`, `exp`, `sqrt`, `log`, `log2`, `log10`, `log1p`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan2`, `hypot`, `sinh`, `cosh`, `tanh`, `acosh`, `atanh`, `floor`, `ceil`, `fix`, `round`, `sign`, `mod`, `rem`, `isnan`, `isinf`, `isfinite`; `sum`, `prod`, `mean`, `any`, `all`, `max`/`min` with their index output (over the first non-singleton dimension, a given one, or `'all'`); `cumsum`, `cumprod`; `dot` and `norm` of vectors; `mtimes` and the transposes; concatenation (`[A, B]`, `[A; B]`, `cat`; host numeric operands are uploaded in the result's class) and `repmat`; indexing, and assignment of a scalar or an array. `G(:)` and other selections of every element in order share the array's buffer. The index output of `max`/`min` is double, computed as f32 on the device (exact below 2^24 elements), so it stays on the device for `gather` but later kernels do not take it.

A function whose real input can need a complex result (`sqrt` and `log` of a negative number, `power` with a negative base and a non-integer exponent, `asin` outside [-1, 1], ...; `DOMAIN_OPS`) raises MATLAB's error on real gpuArray data rather than return a complex result, as MATLAB asks for such inputs to be declared complex (`LOG: needs to return a complex result, but this is not supported for real input X on the GPU. Use LOG(COMPLEX(X))`). This holds on every device: on the CPU reference devices the fallback's result is checked, and on the WebGPU device the kernel sets a flag for an element outside the domain, which the call waits for.

The WebGPU device implements the kernels in WGSL (`webgpuModule.ts`), compiled once per operation and operand kinds; scalars travel in a uniform block. A kernel is posted without waiting, so a chain of operations stays on the GPU until a `gather` (or a condition, a scalar read) waits for it. The helper encodes kernels into one command buffer and submits it when a request needs results, after 128 dispatches, or once the posted calls it has received have run; the batch's uniforms share one buffer. A batch runs in one pair of error scopes, popped without waiting (waiting on them for each kernel made every dispatch a round trip), so a failure is raised by the next request. Batching brought the cost of a small kernel from about 70 µs to 12 µs (Apple M5 Max, Dawn). A readback is slower: Dawn's `mapAsync` takes about 150–200 µs even on an idle queue. NaN is detected on the bits (a shader compiler may assume `x == x`), so `max`/`min` skip NaN as MATLAB does, and `round` rounds half away from zero. Reductions accumulate in f32, splitting a long reduction with few outputs into chunks of 64. The results differ from the host's in the last bits: WGSL allows 2.5 ulp for division, an absolute error of 2^-11 for `sin` and `cos` on [-pi, pi] (and more outside it), and more for the inverse trigonometric functions, and summation order differs; `numbl_test_scripts/gpu/gpuarray_kernels.m` states the tolerances.

## Complex data and the FFT

A complex gpuArray's buffer holds two parts, real and imaginary; on the WebGPU device each is an f32 buffer. Most kernels work on real data, so a complex operation that acts on each part alone runs them on the parts (`GpuKernels.parts`, which gives the parts as real buffers sharing the complex buffer's memory) and joins the two results (`GpuKernels.complex`): indexing and assignment, concatenation, `repmat`, the transposes (the conjugate transpose also negates the imaginary part), `sum`, `mean` and `cumsum`. A complex matrix product is four real ones. Element-wise operations with a complex operand, or that make complex data or take it apart, run in a separate kernel over vec2f values (`celementwise`, `COMPLEX_OPS` in `kernels.ts`): `+ - .* ./ .\ .^`, unary minus, `exp`, `log`, `sqrt`, `sin`, `cos`, `conj`, `complex`, `real`, `imag`, `abs`, `angle`, `==`, `~=`, `isnan`, `isinf`, `isfinite`; `dot` and `norm` of complex vectors use it too. Other operations on complex data (`prod`, `cumprod`, `max`, the ordering comparisons, the remaining functions) fall back to the host.

On the GPU, MATLAB keeps a complex result complex when its imaginary parts are all zero, where the host drops them (`(z + 1i) - 1i`, `z(k)` and `sum` of complex data stay complex); `fft` always returns complex data and `ifft` does unless given `'symmetric'`. The kernels follow this, and so does the fallback: a builtin run on the host for complex input (`KEEP_COMPLEX` in `builtins/gpu.ts`), indexing, and assignment give complex results (`outputToGpu` with `complex`), so the CPU reference devices agree with WebGPU.

`fft(X)`, `fft(X, n)`, `fft(X, n, dim)` and `ifft` of single gpuArrays run on the WebGPU device (`fftKernel`). Each sequence along the dimension is copied, padded with zeros or truncated to `n`, into a work buffer of vec2f values and transformed there by radix-2 Stockham passes, one dispatch per pass; a length that is not a power of 2 uses Bluestein's algorithm, a convolution with a chirp computed by transforms of a power-of-2 length at least 2n - 1. The twiddle factors, chirps and the chirp filter's transform are computed in double precision on the helper and kept for reuse, so the results are within a few multiples of single-precision rounding of the host's (relative errors of about 2e-7 for lengths up to 4097). `ifft(Y, ..., 'symmetric')` reads each sequence's first half and its conjugate mirror, and writes only the real part; the host implements the same option. On an Intel Iris Xe, a 2^20-point transform takes 13 ms (the host, 64 ms) and 1024 transforms of length 1024 take 7.5 ms (13 ms); 1000 transforms of length 1000, by Bluestein's algorithm, take 31 ms, slower than the host's 23 ms. The passes are bound by memory traffic; transforms that do several passes in workgroup memory would be faster.

## Fusion

On a device that evaluates fused expressions (`GpuKernels.fused`), an element-wise kernel does not run at once (`runtime/gpu/fusion.ts`). Its result is a lazy gpuArray (`RuntimeGpuArray.lazy`, a `FusedExpr`: buffer inputs, scalars, and nodes in evaluation order), and an element-wise operation on a lazy operand inlines the operand's expression rather than computing it. Reading the array's `buffer` (a reduction, `gather`, indexing, any non-element-wise kernel) computes the whole expression as one generated WGSL kernel. At the end of each statement (`Runtime.withScope`), `flushPendingGpu` computes the lazy arrays that a slot other than a statement scope holds (a variable, a cell, a field), so a value never stays pending across statements; temporaries consumed within the statement are dropped without being computed, so `y = a .* b + c` runs one kernel. A lazy array held only by a statement still running (an outer statement waiting on a function call) stays pending until its own statement ends. The expression holds its input buffers (`retain`) until it is computed or dropped, so overwriting an input in the same statement (`Q = Q .* 2 + Q`) is safe. Fusion covers operands of one shape or one element, within 8 inputs, 16 scalars and 48 nodes (a larger operand is computed first); implicit expansion and the functions with a real domain (`sqrt`, `log`, ...: they must report an out-of-domain element at once) run as separate kernels. It roughly halves the time of a two-operation chain (`G .* 0.999 + 0.001`: 0.18 ms per operation at 2e6 elements on an Intel Iris Xe, 88 GB/s effective).

In Node, Dawn aborts the process if its device is alive when the helper worker is torn down, so the Node helper shuts the device down (a `shutdown` request) when the process exits. A device with kernels will register gpuArray methods (`classMethod("gpuArray", ...)`) for the operations it runs natively; resolution picks a method of an object argument before the builtin, so the generic path remains the fallback for everything else.

The JIT declines gpuArray values (`typeOfValue` types them as unknown), so code that handles them runs on the interpreter.
