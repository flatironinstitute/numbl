# JIT IR and Codegen

The JIT compiler is the in-tree subsystem under `src/numbl-core/jit`. It lowers the parser AST to a typed intermediate representation, then emits JavaScript (`--opt 1`) or C (`--opt 2`) from the same IR.

## IR

`jit/lowering/ir.ts` defines the IR: discriminated-union expression and statement nodes, each carrying its resolved `Type` (`jit/lowering/types.ts`). Expression kinds include numeric / imaginary / string literals, variables, binary/unary ops, calls (user-function specialization, builtin, runtime helper), tensor build, index load / slice, member load, and cell / struct / handle nodes. Statement kinds include assign, indexed / sliced / member / cell stores, `if` / `while` / `for`, multi-assign, and control flow. Types are fixed at lowering time: codegen never re-decides what an operation means.

## Lowering

`jit/lowering/lower.ts` (the `Lowerer`) walks the AST top-down, tracking variable types per scope and resolving callees through the workspace (`jit/workspace/workspace.ts`, which delegates to numbl's `resolveFunction`). `specialize.ts` produces one `IRFunc` per `(function, arg-type signature, nargout)` and caches it in `Lowerer.specializations`, so repeated calls with the same signature reuse the lowering. A construct the IR can't represent throws `UnsupportedConstruct` / `TypeError` (`jit/lowering/errors.ts`; re-exported as `JitTypeError` from `jit/index.ts`); the executor catches it and declines to the interpreter.

## Backends

Both backends walk the same IR program: `compileSpec` → `jit/codegen/emitJs.ts` for JS; `compileSpecC` → `jit/codegen/emit.ts` for C:

- **JS** emits an ES module string returning `($h) => specFn`, materialized with `new Function(...)`. `$h` carries the host hooks (output sink, plot dispatch).
- **C** emits C source compiled to a `.so` with `cc` and called via koffi; multi-output specs use out-pointer params (see `executors/jit/typeAdapterC.ts`).

Builtins emit through the JIT compiler's own registry (`jit/builtins`): each def supplies `emitJs` / `emitC`. **Runtime snippets** (`jit/builtins/runtime/*.h` C bodies + `*.js` siblings of the same stem) are generated by `scripts/build_runtime_snippets.ts` into two files: the JS bodies and the snippet table into `snippets.gen.ts`, and the C bodies (`C_SNIPPETS`) into `snippets.c.gen.ts`. They are inlined into the emitted module **lazily**: an emitter activates a snippet by name (`useRuntime("jit_...")`), which pulls in its dependencies first, and only activated snippets are included. The C table is split out so the browser worker bundle excludes its ~300 KB of C source: C-JIT is Node-only, so the Node bootstrap (`executors/jit/compileC.node.ts → registerNodeCompileC`) registers `C_SNIPPETS` with the codegen runtime via `setCSnippets`; `codegen/runtime.ts` resolves C bodies lazily and never references the C table in the browser-reachable graph.

Each `.h` declares its table entry in a required first line, which the generator strips from the emitted C:

```c
/* @snippet name=jit_disp_double deps=jit_format_double,jit_host_output */
```

`name` is what emitters activate, `deps` lists the snippets the C body needs (emitted before it), and an optional `aliases=a,b` gives further names for the same snippet (`strcmpi` activates `strcmp.h` as `jit_strcmpi`). The `.js` twin's dependencies are not declared; the generator appends the `.h` twins of the files it imports. `codegen/runtime.ts` builds its registry from the generated `SNIPPET_DEFS` / `SNIPPET_ALIASES`, and `npm run build:snippets:check` (run in CI) fails if the generated files are stale. Builtin defs may import a snippet's exports from `snippets.gen.js` to fold constants with the same code the JS backend runs (e.g. the complex unary-math folds call `jit_csqrt`, `jit_cexp`, … from `cscalar.js`).

## Adding a JIT builtin

1. **Definition.** Add `jit/builtins/defs/<topic>/<name>.ts` exporting a `Builtin` (`transfer`, `emitJs`, `emitC`), or a one-line call to a factory such as `defineUnaryRealMath` (`defs/math/_unary_real.ts`). Register it in `jit/builtins/index.ts`.
2. **Runtime helper** (only when the emitted code calls one). Add the C body to a `.h` under `jit/builtins/runtime/<topic>/`, starting with its `@snippet` header, and the JS body to a `.js` of the same stem. To extend an existing helper (e.g. a new kernel in `tensor_unary_real_math.{h,js}`), just add the functions; a unary-math tensor kernel is found by its export name (`jit_tensor_<name>`, `jit_tensor_<name>_complex`). Run `npm run build:snippets` and commit the regenerated `snippets.gen.ts` / `snippets.c.gen.ts`.
3. **Tests.** Add a `numbl_test_scripts/` script (with `%!numbl:assert_jit` where it should compile) and run it at `--opt 0/1/2`; add a `jit_parity/` case when the result is easy to get subtly wrong across modes.

See [executors.md](../executors.md) for how the executors invoke `compileSpec` / `compileSpecC` and marshal values across the boundary, and [cjit.md](cjit.md) for the C backend specifics.
